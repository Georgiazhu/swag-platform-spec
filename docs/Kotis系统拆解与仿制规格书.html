01执行摘要与核心结论

Kotis Design（kotisdesign.com）成立于 2003 年，总部西雅图，实为远程办公的定制周边礼品服务商，同时自研并运营一整套面向客户的 SaaS 平台。该平台在 G2「Promotional Product Management」品类连续 11 个季度排名第一，客户包括 AWS、Kraft Heinz、MongoDB、DigitalOcean、Bethesda、Meta、Coursera。

最重要的三个判断
  1. 它卖的不是软件，是「托管的仓储 + 履约 + 平台」三合一。平台费可被季度采购额抵扣（≥$5,000/季免平台费），这决定了仿制系统必须把「采购金额」而非「订阅费」当成核心计费锚点。
  2. 系统真正的技术内核是「一套库存、多个门户」。所有 Portal 共用一个 SKU 库存池，Portal 只决定「谁能看、看到什么、什么价、怎么付、要不要审批」——这套「多租户 Portal + 共享库存」模型是整个产品最值得抄的部分。
  3. 面向客户交付的是两个系统，不是一个。对客户是「下单系统」（Portal + MyKotis 后台），对内部是「仓储管理系统」（WMS、收货、盘点、打包发运）。仿制时若只做前端下单而不做 WMS，履约承诺无法落地。

客户可感知的价值

无限门店 + 无限用户不额外收费；实时库存可见；下单后当日发运（12:00 前下单）；98% 准时率；95% 美国地区 2 日达。

最难的工程点

SKU 粒度定义（每个尺码独立成 SKU）、共享库存下的多 Portal 定价、审批流与预算的双重闸门、订单—发货—运单三段状态分离。

最容易被忽略但必须做

PII 脱敏、缺货先发（Short Ship）、Excel/CSV 批量下单、季度账单透明化。这四项是 3.8 分和 4.7 分口碑的分界线。

02Kotis 业务模式与平台全景

2.1 商业模式拆解

Kotis 的收入结构是「商品毛利 + 平台费（可抵扣）+ 运费（10% 加价）+ 仓储履约费」。其设计意图非常明确：平台费是一道收入闸门，但可以用采购额直接抹平，从而让客户「买得越多、平台越免费」，把自身锁进客户的采购预算里。

纯 SwagCore首单最低 $500，无平台费在线订单管理、订单追踪、专业设计服务、海外采购与国际运输
平台

计费规则中的关键细节（仿制时容易漏）
  • 季度采购额 < $5,000 时平台费按 $499/月 计；≥$5,000 则整个季度豁免。
  • Standard 及以上有 $2,500 一次性实施费，Core 无。
  • 首月不足整季不收平台费，且该部分采购额可计入下一完整季度的 $5,000 门槛。
  • 采购额不按比例摊分、不向后追溯，按滚动四个季度合计在季末结算。
  • 运费加价 10%；Economy 渠道走全承运商实时比价。
  • 超出 SKU / 托盘额度不立即报错，季末按超出量计费，或引导客户升级套餐。

4.1 兑换门户（Redemption）完整机制

这是 Kotis 差异化最强、也最值得完整抄的一块逻辑：

  1. 发码：客户自助批量生成（Generic-use Codes），导出 CSV 用于邮件合并；也支持 Kotis 代发品牌邮件（主题行、Banner/Logo、正文富文本可编辑）。
  2. 积分额度：每个码可带积分值。终端用户可任意加购，结算时总额不得超过码的积分上限；单次使用，结账后剩余积分作废；结账页显示此提示。
  3. 默认一件一码：Redemption Portal 默认每码限选 1 件，可由 Program Manager 调整为指定件数。
  4. 核销追踪：码状态 unclaimed / claimed / hidden，记录 opened、opened_date、claimed_date、order_number。
  5. 提醒未使用者：Kotis 可对未核销用户发提醒（需客户提供邮箱与姓名清单）。
商业设计洞察

兑换码同时承担「预算控制」和「防薅羊毛」两个职能：预算额度 = 码面值，无需额外账本；码与收件人绑定（可带 email/first_name/last_name），天然形成可追溯的发放台账。仿制时务必保留「码 → 订单」的强关联与状态机。

5.1 端到端下单主流程

步骤节点行为与规则

4提交系统校验：库存 / 预算 / 限购 / 访问码 / 兑换码有效性
5（仅 Non-CC）审批生成待审批订单 → 触发审批人邮件 → 审批人可改数量 / 改运输等级 / 改需求日期 → 批准或驳回
6付款CC 门户走 Stripe Connect；红色项由 Kotis 商户账户代收

9发货邮件发运即发邮件 + 运单号 + 轨迹

5.2 审批流规格（Approval）

配置维度

  • 门户级审批人（必配，激活该功能的开关）
  • 位置级审批人：一个 Portal 配多个 Location 时可分别指定
  • 多个审批人时：全部收到邮件，任一人处理即生效
  • 管理员天然拥有审批权，但只有指定审批人收邮件
  • 未启用 Access List 时，所有金额（含 $0）订单均需审批

审批人可执行的动作

  • 批准 / 驳回（驳回需填原因，原因随邮件发给下单人）
  • 修改商品数量
  • 升降运输等级（Shipping Method 下拉）
  • 调整 Need By Date
  • 查看该用户组的剩余预算
邮件触发点（共 4 类）
  1. 下单人：「订单待审批，尚未发货」
  2. 审批人：含下单人、商品明细、剩余预算的审批链接
  3. 下单人：批准后「已批准」/ 驳回后「已驳回 + 原因」
  4. 下单人：发运后「已发货 + 运单号」

5.3 预算与用户组规格

概念定义
User Group按「经理 / 部门 / 办公地 / 任意维度」切分订单归属，用于追踪用量与支出。用户可属于 1 个、多个或 0 个组；组人数不限
命名规范官方建议按「部门 - 地点」复合命名，如 Marketing - Seattle
组级能力① 指定审批人 ② 设置预算额度 ③ 结账页专属自定义下拉（如「部门」「尺码偏好」）
预算规则预算耗尽 → 该组用户无法再下单，直至人工重置。结账页余额以红色显示（制造消费提醒）
报表关联Sales Report / Shipment Report 含 User Group 列；下载 CSV 后可按组筛选
典型场景Marketing 季度 $5,000 / HR 季度 $10,000；销售经理按人分配客户礼品额度；不同办公地独立额度

5.4 批量下单（CSV / Excel）

这是高频刚需（一次给几十上百人发礼品）。Kotis 的实现方式值得注意——并非自助上传，而是把 CSV 邮件发给客服团队，由客服代提交。

模板规则

  • 必须与官方模板完全一致，否则不提交
  • 地址字段最长 30 字符
  • 禁止特殊字符（如 ą \a ę）
  • 州必须写 2–3 位缩写
  • SKU 格式：38978-1-L；多 SKU 逗号分隔 38978-1-M,38978-4-OSFA
  • 数量为 1 时写 1；多 SKU 数量对应写 1,1
  • Unique Key 留空，由客服回填
  • 一单只能有 Packing Slip Note 或 Handwritten Note，不能并存
  • 国际单必须有收件人邮箱 + 电话（否则卡关务）

客服可代补字段

  • 运输方式
  • 统一补一个邮箱（不发单号追踪时用）
  • Bill to Job Number / Customer PO
  • 全为无尺码商品时补 OFSA-OS
  • 可选字段：Instructions、Packing Slip Note、Handwritten Note、Need By Date、Receiver Email、Receiver Phone
仿制建议：把这一步做成自助

Kotis 让人工代劳，说明CSV 模板严格校验的体验很差。仿制系统应做成「上传 → 自动校验 → 逐行报错（定位到行号与字段）→ 预览确认 → 批量入库」，并支持 Excel 直接拖入。这是可明确的体验差异点。

5.6 后台自助下单（Inventory Management 下单）

Program Admin 最快的下单路径，也是「多收件人 CSV 之外」的轻量方案。表单字段：

  • 商品行：加数量；缺货项会高亮提示
  • Shipping Method：选承运商 + 时效；Economy = 最低成本运费
  • Need by Date：覆盖所有运输方式，系统会自动加急以赶期。不急就别填
  • Ship On or After Date：未来工作日，到期前不发货
  • PO#：可自定义标签的附加数据字段（默认叫 PO#，字段名可改）
  • Include return labels：随箱附回程退货标签（国际/危险品不可用）
  • Upload shipping instructions：上传发货说明或文件（如展会）
  • Add note to recipient：打印在装箱单上的文字
  • Receiver info is different：国际单必填——收件人电话 + 邮箱，过关必需

06仓储管理系统功能规格

6.1 SKU 定义（最易做错的一处）

Kotis 的 SKU 规则

每个尺码算一个独立 SKU（S/M/L/XL = 4 个 SKU）；一个颜色 2 个 SKU。同一 SKU 可以有任意数量（「货架上一个箱子 = 一个 SKU」）。预组套（Pre-kit）算 1 个 SKU。SKU 直接决定仓储费（套餐额度按 SKU 数计）。

6.2 收货与入库（IIR, Incoming Inventory Request）

入库是仓储系统的入口。Kotis 用「在途登记单（IIR）」把「货在路上」变成可见对象，避免到货时才知道有什么。

IIR 字段说明
Reference #仓库用于关联到货包裹的编号——应打印或贴在包裹内外的装箱单上（可填运单号 / PO# / SKU#）
Est. Arrival预计到仓日（Kotis 代产则按「生产周期 + 在途时间」自动算）
Vendor供应商名；Kotis 代产时自动显示 "Kotis"
Tracking运单号
Notes其他说明
Size（逐项数量）每个 SKU / 尺码分别填数量

IIR 首页是一张在途表：Reference / Est. Arrival / Vendor / Delivered（运单显示已送达的日期）/ Received（仓库实际签收并开始入库的日期）。仅支持已有 SKU 的 IIR，新商品须先联系 Program Team。

6.3 库存盘点（Cycle Count）

  • 仓库用移动设备连 WMS 执行盘点
  • 单次盘点 session 限 30–60 分钟，避免「计数疲劳」；超时换人或休息 15 分钟
  • WMS 只提示盘点在库数量 0–10 且近 60 天有订单的 SKU（低库存 + 快周转优先）
  • 差异必须当场双人复核；仓库经理复核所有 ±5 件以上的调整
  • 库存准确率承诺 ≥98%（按价值计，非件数），超出 2% 的损失由 Kotis 赔付
  • 因入库数量错误而从未实际存在的数量（如入库报 1000 实产 500），不计入 2% 阈值——这是很精细的设计

6.4 拣货与包装

Pre-kit（预组套）

  • 适合：呈现很重要（棉纸、定制胶带、手写卡 5×7 非光面、可拍样板照片确认）
  • 适合：发货要快（单 SKU 套件 24 小时内可拣包）
  • 适合：多件小商品（防错、提速、提升开箱体验）
  • 组套后计为 1 个 SKU

Bundling（捆包）

  • 同款商品按包装数量合并（如 100 张贴纸一包、25 支笔一袋）
  • 常见规格：10 / 25 / 50 / 100
  • 方式：热缩膜、橡皮筋、胶袋
  • 成本 $0.50–0.85/包
  • 收益：减少出入库事务、提升拣货准确率、消化滞销

另有 SKU Add-on 功能：给某 Portal 的每一笔订单自动追加一个商品（如感谢卡、贴纸），官方建议每 Portal 只配 1 个。

6.5 仓储条码策略（反直觉设计）

Kotis 官方结论

「为什么条码对客户没有帮助」——Kotis 不给单个商品贴条码，而是以「货架上的箱子」为 SKU 单位。理由是：整箱同款商品上架时不需要逐件扫描，只有拣货出库时才扫一次箱子。仿制时应理解这一取舍：单件级条码 = 更准但更慢；箱级 = 更快但要求整箱出库。若客户要散件发货，则必须回到单件条码 + 更复杂的拣货流程。

6.6 入库时效 SLA

货品来源入库时效（自物流显示送达起）
Kotis 代产商品2 个工作日（周一到货 → 最迟周三下班前入库）
非 Kotis 生产的商品4 个工作日
新签客户承接既有库存7 个工作日
展会器材退回2–5 工作日（+ 干洗另加 5–10 天）
一般退货处理5 个工作日
产品照片上架入库完成后 3 个工作日内（大批量到货再 +1–2 天）

异常：缺箱/不全的货 +1 天（共 3 个工作日）；无预告到货（无事先通知内容）→ 需 5 个工作日窗口且不可享赔付。

7.1 三级管理员

7.2 Item Access Group（库存内部隔离）

  • 目的：把库存按部门/团队切分，Manager 只能看到并下单自己负责的货
  • 规则：一个商品只能属于一个访问组；未分配访问组的商品仅 Owner 可见
  • Manager 可见门户的条件：该门户至少含 1 个其有权查看的访问组商品
  • 配置：Program Settings → Edit Manager access group permissions → 勾选矩阵

7.3 门户级用户管理

  • 新增用户 → 系统发邀请邮件 → 用户自设密码（该流程仅对新用户）
  • Users 页面可查看用户、是否兼管理员、删除用户、新增用户
  • SSO：Google Workspace / Azure Active Directory / Okta / SAML —— 不需另建 Kotis 账号，管理员无需手动开通
  • MFA：绑定任意验证器 App
  • 访问码（Access Code）：整个 Portal 用单一密码保护，未输入无法查看商品
  • 用户组下拉（Custom Option）：可在结算页按组显示专属下拉（如「部门」「尺码」）
  • Custom Input Label + Custom Dropdown Values：商品级自定义输入框/下拉
权限设计的核心洞察

Kotis 的权限是三层叠加的：① 角色（Owner/Manager/Accounting）控制「能干什么」；② 访问组控制「能看到哪些货」；③ 用户组控制「花谁的钱、谁审批」。三者正交。仿制时务必把「预算归属」与「可见性」分开建模——Kotis 就是用 User Group 同时承载了预算和报表分组两个职责。

12计费模型与商业设计

12.1 平台费的抵扣逻辑

规则
  • 平台费 $1,500/季（约合 $499/月），季度采购额 ≥ $5,000 即全额豁免
  • 采购额在订单进入生产时计入（不是下单时），因此客户必须在季末前完成打样审批 + 签字 + 付款
  • 财政季度：Q1 = 1–3 月，Q2 = 4–6 月，Q3 = 7–9 月，Q4 = 10–12 月
  • 季末会提前提醒客户是否达到门槛
  • 剩余季度不结转（Kotis 明确不鼓励压货）

12.2 仓储容量计费

计量定义
SKU独立计库存的单位；每个尺码独立；预组套计 1 个
托盘40"×48" 木托，可叉车搬运，堆高至 5 英尺。参考容量：约 2,000 件 T恤 / 1,500 件长袖 / 1,000 件卫衣 / 1,500 个水瓶
货架取货位仅设计存放 1–2 箱；同款多箱转存托盘长期存放
超额处理① 增加采购额自动升档 ② 减少商品数 ③ 季末按超出量计费

12.3 包装费边界

平台费覆盖标准包装：胶袋 + 常规库存纸箱。不覆盖异形定制包装（海报筒、易碎品、电子产品、烤炉、帐篷等）。官方建议大量寄送异形物品时在生产阶段预包装。

14.4 关键工程难点与对策

难点问题本质对策
并发超卖多个 Portal 共享一个库存池库存扣减走数据库行锁或乐观锁（version 字段）；下单走「预占 → 支付确认 → 实扣 → 超时释放」
SKU 爆炸尺码×颜色导致 SKU 数膨胀，推高仓储费引入「款式(Style) + 变体(Variant)」两层建模，费用只按 Variant 计；提供 SKU 合并工具
审批与预算竞态审批人改数量后预算可能已超；两人同时批准同一单审批动作与预算扣减在同一事务内；订单加版本号做乐观锁
多口径财务对账Order 与 Shipment 金额不一致导致季度账单争议建「财务口径中间层」：所有报表与账单统一从 Shipment 派生；差异单独设调整科目
门户配置爆炸每个 Portal 十几个维度组合，配置项互相影响配置项字段化存储 + 继承（客户级默认 → 门户级覆盖）；提供「预览 + 沙箱 Portal」
PII 合规导出报表泄露收件人信息PII 字段在序列化层统一脱敏；导出单独走审计日志；保留 City/State/Zip/Country
多租户隔离跨客户数据泄露 = 重大事故所有查询强制 tenant_id 过滤（可用 PostgreSQL RLS 或 ORM 全局 scope）；越权测试纳入 CI

15.1 第三方评测暴露的 Kotis 弱项（= 你的切入点）

弱项评测原话要点你的机会
CSV 下单体验差CSV 必须严格匹配模板，否则客服退回或代改做自助上传 + 行级校验 + 错误定位 + 预览确认

审批流证据不足公开材料未充分展示多级审批工作流审批链 + 审批 SLA + 委托代理 + 批量审批

15.2 合规与运营风险

风险说明与应对
危险品合规打火机、电池、喷雾、磁性物品等需特殊承运与标识；UPS 对危险品时效不担保。需建危险品 SKU 标记 + 发运拦截 + 承运商限制
国际关务印度需 KYC 表；各国需进口文件（UPS Import & Export Regulations）。需按国家配置必填表单与申报规则
加州 Prop 65加州销售需合规警示，涉及特定材料/化学品
税俄亥俄、犹他销售税豁免需表格备案（TC-721 等）；CC 门户涉及销售税代收代缴
库存专有条款Kotis 合同含 Inventory Exclusivity（客户发往 Kotis 仓库的货，Kotis 有权投标收购）——这是 Kotis 的商业护城河，仿制时不要照抄
SOC 2 / GDPR企业客户要求年度 SOC 2 Type 2 审计；GDPR 下 Kotis 为数据控制者，支持访问与删除请求
SSO 无测试模式Kotis 的 SSO 一旦启用覆盖全平台，不提供测试环境——这是明显的体验缺陷，仿制时应提供沙箱 IdP 联调
