# 落地差距分析：Cyndi 现状 vs Kotis 能力基线

> **本文档的用途**：让接手人在不重读 Kotis 全部资料的前提下，知道「现在到哪了、还差什么、怎么排期」。
>
> 对应资料：`docs/Kotis系统拆解与仿制规格书.html`（能力基线）、`docs/API契约与数据模型速查.md`（接口与数据模型）
>
> 分析基准：`Georgiazhu/cyndi-global-website` @ `main` 分支（2026-10-29 快照）

---

## 0. 一句话结论

现有项目是一个**做得不错的定制化电商前端 + 物流查询**，但按 Kotis 的标准衡量，**仓储管理和下单管控两块几乎还是空白**。

差距的核心不是「缺功能」，而是**缺数据模型**：`product_skus` 表明确写着「无库存字段（按订单定制生产）」，`orders` 表只有一个 `status TEXT` 字段。所有仓储、审批、预算、报表能力都依赖这两张表先行改造。

### 1.3 值得保留的既有优势

不要在改造中弄丢这几点，它们是当前实现优于 Kotis 公开资料的地方：

1. **SPU = 物流 productNo 打通**（`CY-{品类}-{序号}`）。这套编号同时是商城款号和物流产品号，跨模块追溯能力强于 Kotis 的纯 SKU 体系。
2. **物流可视化带仓库实拍图**（`warehouseImages` + `events[]` 带中英双语描述）。Kotis 只有运单号和轨迹状态，没有仓库影像。
3. **中英双语字段**（`productNameZh` / `originZh` / `titleZh` / `descriptionZh`）在数据层就做好了，不依赖前端翻译。
4. **多币种在数据层区分**，而不是前端换算。

## 3. 数据模型改造建议（重点）

### 3.1 必须先拆的两张表

#### 3.1.1 `orders` → 主表 + 行表

**现状问题**：`items_json` 把订单明细压成一段 JSON。后果是——改单、拆单、退款、按 SKU 统计、做「原始数量 vs 实际数量」对账，全部要做 JSON 解析，且无法建立外键。

**建议拆为**：

```
orders（主表）           order_lines（行表）
├─ order_no (PK)         ├─ id (PK)
├─ customer_id           ├─ order_no (FK)
├─ customer_name         ├─ sku (FK -> product_skus)
├─ customer_email        ├─ product_name   ← 快照
├─ portal_id             ├─ selected_color  ← 快照
├─ source                ├─ selected_size   ← 快照
├─ status                ├─ price           ← 快照
├─ subtotal / shipping   ├─ quantity
├─ discount / tax        └─ original_quantity  ← 保留原始量
├─ total                            ← 支撑中途取消后的对账
├─ approver_email
├─ budget_group_id
├─ need_by_date
├─ ship_on_or_after
├─ po_number
└─ created_at
```

**保留快照字段的理由**：商品价格、名称随时会变，历史订单必须留存下单时的值。Kotis 的报表里 `Product` / `Color` / `Size` / `Price` 都是快照而非关联读取。

#### 3.1.2 新增 `inventory` 表

```sql
CREATE TABLE inventory (
  sku              TEXT PRIMARY KEY,   -- FK -> product_skus.sku
  physical_qty     INTEGER NOT NULL DEFAULT 0,
  available_qty    INTEGER NOT NULL DEFAULT 0,
  reserved_qty     INTEGER NOT NULL DEFAULT 0,
  low_stock_threshold INTEGER DEFAULT 0,
  cost_cents       INTEGER,            -- 库存价值，赔付与毛利核算用
  updated_at       TEXT NOT NULL
);
```

> ⚠️ **D1 是 SQLite，不支持 `AUTOINCREMENT` 之外的自增语法差异不大，但要注意**：
> - SQLite 无 `JSONB`，用 `TEXT` 存 JSON（与现有 `items_json` 一致）
> - 无 `TIMESTAMPTZ`，用 `TEXT` 存 ISO8601 字符串（与现有 `created_at TEXT` 一致）
> - 无 `SERIAL`，用 `INTEGER PRIMARY KEY AUTOINCREMENT`（与现有 `product_colors` 一致）
> - **并发写是最大风险**：D1 单写者模型 + Workers 并发请求 → 扣减库存必须用条件更新防超卖：
>   ```sql
>   UPDATE inventory SET available_qty = available_qty - ?1, reserved_qty = reserved_qty + ?1
>   WHERE sku = ?2 AND available_qty >= ?1;
>   ```
>   然后检查 `changes()` 是否为 1，为 0 则说明库存不足，直接失败。**不要先 SELECT 再 UPDATE。**
> - D1 支持 `batch()` 事务，可把「扣库存 + 建订单 + 建订单行」包进同一批

### 3.2 D1 vs PostgreSQL 的适配差异

`docs/API契约与数据模型速查.md` 里的 DDL 是 PostgreSQL 版本（贴近 Kotis 原生实现）。落到 D1 时按下表改写：

| PostgreSQL | D1 (SQLite) | 说明 |
|---|---|---|
| `BIGSERIAL PRIMARY KEY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | |
| `TIMESTAMPTZ DEFAULT now()` | `TEXT DEFAULT (datetime('now'))` | 或应用层写 ISO 串 |
| `JSONB` | `TEXT` | 与现有 `items_json` / `attributes_json` 风格一致 |
| `NUMERIC(6,4)` | `REAL` | 税率用 REAL 足够 |
| `TEXT[]` (数组) | `TEXT` 存 JSON 数组 | |
| `INET` | `TEXT` | |
| `CHECK` 约束 | 支持 | 但建议也在应用层校验 |
| 事务 | `db.batch([...])` | 单条 SQL 无显式事务；多语句用 batch 包裹 |

## 5. 实施路线建议

以「能跑通一个完整业务闭环」为里程碑，而非「按功能清单逐个补齐」。

### 阶段 A：把地基打平（无新功能，全是改造）

**目标**：让后续所有仓储功能有表可依。

1. 新增 `inventory` 表 + SKU 库存初始化脚本（现有 SKU 先全部设为 0 库存，走「按订单生产」存量逻辑）
2. `orders` 拆出 `order_lines`，历史 JSON 写迁移脚本回填
3. `orders` 补字段：`source` / `portal_id` / 金额分项 / `need_by_date` / `po_number` / `approver_email`
4. 新增 `shipments` / `shipment_lines`

> ⚠️ **拆表是高风险操作**，务必：先备份 D1 → 写迁移脚本前在本地验证 → 小批量灰度 → 保留回滚脚本。

### 阶段 B：单门户的仓储闭环

1. 后台「库存管理」页：库存列表 + 数量调整（带原因码）
2. 后台自助下单（从库存直接下单）
3. 拣货打包工作台：待发订单池 → 生成发货单 → 填运单号 → 状态流转
4. 物流记录与发货单打通（现有 `logistics_records` 升为发货单的视图，或保留独立但关联）

### 阶段 C：管控能力

1. `portals` 表 + 门户管理后台 + 商品上架配置
2. 审批流（含审批人、驳回原因、改数量）
3. 预算组 + 余额扣减 + 耗尽锁单
4. 管理报表（先做 Sales / Shipment / Inventory 三张）

### 阶段 D：规模化

1. 兑换码 + 积分
2. CSV 批量下单（自助上传 + 行级报错）
3. PII 脱敏 + 报表导出
4. 客户 REST API（按 `docs/API契约与数据模型速查.md` 的 6 个端点）
5. 门户主题化 / 多品牌定制

## 6. 差异化机会（Kotis 的公开弱点 → 我们的优势）

这些是 Kotis 第三方评测明确指出的弱项，**建议在对应功能实现时直接超越**：

| 弱项 | Kotis 的做法 | 建议做法 | 落地阶段 |
|---|---|---|---|
| CSV 批量下单 | 必须严格匹配模板，且**人工发邮件给客服代提交** | 自助上传 + 行级校验 + 精确到行号和字段的报错 + 预览确认 | 阶段 D |
| SSO | 启用即覆盖全平台，**不提供测试模式** | 提供沙箱 IdP / 测试租户 | 阶段 D |
| 打样审批 | 服务式人工流程，无版本控制工具 | 版本化工作流 + 图片区域标注 + 多轮留痕 | 阶段 C+ |
| 门户配置 | 依赖交付团队协助，非自助 | 自助品牌主题 + 权限模拟器（预览某人能看什么） | 阶段 D |
| 报表 PII | 自动脱敏（这点应学） | 学其脱敏，同时提供「申请查看 PII」的授权流程 | 阶段 D |
| 国际单信息 | 靠人工检查 CSV 补齐 | 表单强校验 + 缺项阻断 | 阶段 B |
| 库存盘点 | 依赖 WMS 移动端 | 先用后台表单 + 摄像头扫码（手机浏览器即可） | 阶段 B |

## 7. 待确认的业务问题

接手前建议向业务方确认，这些直接影响表设计，改起来成本高：

1. **库存归属**：Cyndi 自己的成品仓，还是客户寄存在 Cyndi 仓（Kotis 的模式是后者，占 SKU 配额）？→ 决定是否需要 `program_id` 维度的库存隔离。
2. **履约模式**：继续「按订单生产」，还是要引入「提前备货到仓」？→ 决定阶段 A 的库存初始化策略，以及 P0 的紧急程度。
3. **多门户需求**：是否真的需要「一个客户开多个独立品牌站」？还是只需要「按客户配置品牌主题」？→ 差别很大，前者是 P0，后者可降到 P2。
4. **是否收仓储费**：按 SKU 数 / 托盘 / 订单量计费？→ 决定是否需要配额与计费引擎。
5. **是否要开客户 API**：有无客户需要用自有系统调库存/下单？→ 决定阶段 D 的优先级。
6. **币种与结算**：现有支持 USD/CNY，混合币种下订单金额如何记账（汇率锁定时点）？
7. **谁是审批人**：Cyndi 内部员工？还是客户的 HR/行政对接人？→ 决定审批流是内部闭环还是外部角色。

## 8. 环境与命令速查

```bash
# 仓库
git clone https://github.com/Georgiazhu/cyndi-global-website.git
cd cyndi-global-website

# 本地开发（含 D1 本地库）
npx wrangler dev

# 应用迁移到远程 D1
npx wrangler d1 migrations apply cyndi-logistics --remote

# 本地库重置
npx wrangler d1 execute cyndi-logistics --local --file=./schema.sql

# 部署
npx wrangler pages deploy product-showcase/dist --project-name=cyndiglobal
```

数据库绑定名 `DB`，R2 绑定名 `MEDIA`，线上库 `cyndi-logistics` / bucket `cyndi-products`。
